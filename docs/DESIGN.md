## The three folders

A kit is one folder with three inside, so a new version can replace the code without touching anything else:

| Folder | What's in it | Written by |
| --- | --- | --- |
| `TinfoilKit/app/` | The code exactly as released (this repo's `kit/`), with `kit.json` as the standard list | Only `./kit update`, which replaces it. It can be deleted any time for a new download's app folder |
| `TinfoilKit/downloads/` | `bin/`, `models/`, `library/`, `maps/`, `installers/`, `INVENTORY.md`, and `.partial/` (archives still downloading). Item destinations (`models/Tiny`) and `state.json`'s paths are inside it | `./kit sync` |
| `TinfoilKit/data/` | The person's: `kit.json` (what goes in their kit), `logs/`, `notes.txt` and `places.json` (Notes and the map's home and pins), and new features' files. The kit's own records are in `data/.kit/`: `state.json`, `share.json`, the lock, caches, the built `portal.html`, `kit.base.json`, the update being unpacked | Every command |

- The kit folder is the code folder's parent when the code folder is called `app` (any case) and isn't a git checkout. In a git checkout the app folder is `kit/`, with `downloads/` and `data/` inside it (git-ignored); a checkout from before `kit/` had them at its top, and `ensureLayout` moves them in. In the program: `checkout`, `kitLayout`, `kitOf`, `appDir`, `dlDir`, `dataDir`, `metaDir`. The wrappers, launchers, SETUP, UNINSTALL and the Mac app work it out the same way.
- A `downloads/` folder is what says the kit has been set up: SETUP's first run looks for it.
- Beside the three folders are what a person opens first (`topFiles`, which `ensureTop` puts there at the end of every command but `open`, once the kit has `downloads/`): `Open Tinfoil Kit.command`, `Open Tinfoil Kit for Windows.bat` and `Read me first.txt`. No one file starts with a double-click on all three systems, since each goes by the file's ending (Linux by its content and the file manager), so there's a launcher for each, and they start the ones in `app/`, with the same options. The read-me opens anywhere: plain ASCII, CRLF, lines Notepad needn't wrap. Only in a folder of the kit's own (alone, or called `TinfoilKit`), never a git checkout's, whose launchers are at its top already, nor one from before the three folders, whose code `ensureLayout` moves from its top into `app/`, launchers and all. The program writes them, so a download's quarantine or Mark of the Web never reaches them. `data/.kit/top.json` holds the SHA-256 of what it last wrote: it replaces a file only while that still matches, so one the person changed stays theirs, and one that's gone comes back.
- `data/kit.json` starts as a copy of `app/kit.json`. When `app/kit.json` differs from `data/.kit/kit.base.json` (the standard list it last took in), every command first merges the two (`ensureConfig`, three ways, as in [Updating](#updating-the-kits-own-code)). So a new version's sources reach the kit whether `./kit update` installed it or someone put a new app folder in by hand.
- New features keep the person's files in `data/` and their downloads in `downloads/`, never in `app/`.
- A kit from before the three folders moves into them by renaming, so nothing downloads again (`ensureLayout`, which every command runs first; SETUP runs `./kit layout` for it, on Windows from a copy of the program in TEMP, since Windows won't rename the folder of a running program, with `KIT_CODE` naming the code's folder): its code into `app/`; `bin`, `models`, `library`, `maps`, `installers` and `INVENTORY.md` into `downloads/`; `.kit/downloads` into `downloads/.partial`; and `kit.json`, `logs` and `.kit` into `data/`. `.kit` moves last, so a move that stops partway finishes on the next run. A git checkout's code stays where it is. Starting with the computer (home server) is rewritten to run from `app/`.
- The kit never moves or deletes someone else's files: `./kit place` moves a kit folder only when it holds nothing but `app`, `downloads`, `data` and the files beside them (and what computers leave in any folder: `.DS_Store`, `desktop.ini`, `Thumbs.db`, `._*`), and UNINSTALL deletes it only then, or when it's called `TinfoilKit` or is a git checkout. An app folder put somewhere on its own, like the Desktop or Downloads, has other things beside it, so SETUP asks for it to be put in a folder of its own, and UNINSTALL deletes nothing. The program also refuses the home folder or a drive's top as the kit folder.
- A kit whose app folder was deleted (it has `data/.kit/state.json`) still counts as a kit: SETUP from a new download finds it, and `./kit place` copies the new app folder into it.
- The signed update archive (`tinfoilkit-TAG.tar.gz`) holds the app folder's files at its top, which older updaters expect. The downloads for the setup command (`TinfoilKit.tar.gz`, `TinfoilKit-Windows.zip`) are `TinfoilKit/app/...`. Each is `git archive` of `kit/`, with the programs built from it and the license, README and THIRD-PARTY.md from beside it (`build.sh archive`).

## Commands

`./kit --help` lists them. What each one decides:

- `./kit plan [--only WORDS]`: preview what sync would do, and how long it takes. Before a kit's first big download (no `download_speed` yet), it times the connection: a few seconds of the biggest book or model it needs, over eight connections as sync gets it, thrown away (`measureSpeed`; models and books only, since their hosts serve most of the kit). It skips that while a sync holds the kit.
- `./kit sync [-y] [--force] [--only WORDS]`: download and update everything. `--force` ignores the free-space margin.
- `./kit verify [--quick] [--fix]`: re-check checksums. `--quick` checks sizes only; `--fix` deletes corrupt files so the next sync replaces them.
- `./kit status`: what's installed, and the size of each item.
- `./kit search WORDS`: search the Kiwix catalog for more books to add.
- `./kit test [--model NAME]`: start every server offline and check that each one answers.
- `./kit update [--force] [--yes]`: install the newest signed release of the kit's own code, keeping kit.json changes. At a keyboard it shows what's new and asks first; `--yes` doesn't ask. `--force` reinstalls the current one.
- `./kit pins`: write `tools/pins.json`, the newest build of every program with its SHA-256 (before a release; the `pin program builds` workflow runs it weekly).
- `./kit estimate [--essentials|--starter|--rest|--json]`: the GB this kit.json needs, from the builder's sizes, offline. `--json` adds the items it counts (`estimateItems`), which the website test compares with the builder's ticks. `--rest` (for SETUP): the GB a try-it kit doesn't have yet, a tab, and how long that takes at the speed the last sync measured (`download_speed` in state.json, bytes a second, kept once a sync has downloaded 100 MB, or plan's timing before that).
- `./kit fit [--ask|--skip-too-big|--restore|--json]`: which AI model this computer runs, and the enabled ones too big for its memory (a model may use 60% of memory, as the launcher decides). `--ask` asks whether to get those (SETUP does); `--skip-too-big` and `--restore` switch them off and back on in kit.json. Skipped ones go in kit.json's `models_off_for_memory`, so SETUP offers them back on a bigger computer.
- `./kit space PATH [--json]`: whether all of the kit, and just the essentials, fit at PATH: `fits` (leaves 10% of the computer's disk or 5% of a drive free), `tight` (fits, leaving less) or `no`, then GB free, in all, needed and worth leaving free.
- `./kit essentials [on|off]`: get just the essentials from now on, or everything again (kit.json's `essentials_only`: the programs, the maps, priority-1 books, the model this computer runs and the smallest one). `plan` and `sync` take `--essentials` for one run.
- `./kit starter [on|off]`: get just the try-it kit from now on, or everything (kit.json's `starter_only`; `plan`, `sync` and `estimate` take `--starter` for one run). The try-it kit is this computer's programs except Java, the map's tiles (no roads or address search), and the models and books marked `"starter": true`, even switched-off ones: those are samples, which the next full sync removes once it checks out (`dropSamples`). A sync of the try-it kit counts as complete (`last_sync`), and leaves the other items' unfinished downloads alone. `./kit test` skips address search and directions on it. Without on or off: how big the rest is, and how long it takes.
- `./kit pick [--recommended|--essentials|--everything] [--region PLACES] [--wikipedia CODES] [--wikipedia-size SIZE] [--no-ai] [--models IDS] [--skip IDS] [--add IDS]`: what goes in, as the website's kit builder picks it; SETUP hands it all of its what-goes-in options, so its line and the builder's make the same kit (`tests/site_test.py` runs the builder's lines through it). A preset puts the models, books and map back as the standard list (`app/kit.json`) has them (Essentials also sets `essentials_only`, Everything switches everything on), leaving where you live, Wikipedia's languages and size, extras and hand-added entries alone (`presetChanges`); without one, the options change the kit as it is. Where you live and Wikipedia are `./kit region`'s, applied only when they differ, so saying them again keeps the map's hand-set keys. The other options switch models, books, extras or the map by name, keeping kit.json's layout. A name is an id, `maps`, a whole part (`models`, `library`, `extras`), a book's name up to its first underscore (`wikipedia`: every language) or a site's name (`stackexchange`, `libretexts`). What `--models` and `--add` name gets `"essential": true`: it comes even with just the essentials, and `fit --skip-too-big` keeps it. So does Wikipedia when `--wikipedia-size` comes with just the essentials: the size said wins over the essentials' stand-in. Everything is checked before anything changes (exit 2 for a name or two presets, 1 for a place or size). `--ask`: the builder's choices in a terminal (a preset, or each part). Any of these sets `"picked": true` in kit.json's settings, so SETUP doesn't ask again. No options: what's on, the sizes and the time to download.
- `./kit remove NAME`: delete what an item downloaded, its unfinished downloads too, and switch it off. Switching an item off alone keeps its files, so skipping one update loses nothing.
- `./kit copy [DRIVE] [--essentials|--maps|--everything] [--ai] [--models IDS] [--only IDS] [--add IDS] [--skip IDS] [--notes] [--erase NAME] [--yes] [--json]`: copy the kit onto another drive, as much as fits ("Copies" below).
- `./kit drives [--json]`: the plugged-in drives with format, GB free and why one won't do. `--json` adds this computer's free space and what the kit needs.
- `./kit kits`: the kits set up before, on this computer and on plugged-in drives.
- `./kit place DEST`: move the kit to DEST (copy it to another disk) and print its new folder.
- `./kit share [on|off|new-code] [--code CODE] [--qr]`: share the kit on the home network behind an access code (kit.json's `share_on_network`), and show the address, the code and a QR code.
- `./kit autostart [on|off]`: start the kit whenever the computer starts (a systemd user service, a LaunchAgent on a Mac, the Startup folder on Windows).
- `./kit open [--share] [--model=NAME] [--no-browser] [--no-maps]`: start the kit; both launchers run it.
- `./kit region [PLACE] [--wikipedia CODES] [--wikipedia-size SIZE] [--languages] [--sizes] [--find WORDS]`: where the person lives (the maps' area, roads, address search, home, units) and Wikipedia's languages and size, in `data/kit.json`. Several places with commas, where they live first: places nearby get street detail and directions too, and their road data is merged into one file for GraphHopper (`pbf.go`). Sizes: `all` (all_maxi, the default), `all-text` (all_nopic), `top` (the best 50,000 articles: top_maxi), `top-text` (top_nopic) and `top-intros` (top_mini, opening paragraphs only), `wikiSizes` in the program. A language without that edition gets the biggest smaller one it has (`wikiEdition`); `--sizes` lists only the sizes every chosen language comes in (`sizeChoices`), with GB. A swap keeps the entry's other settings (priority, `refresh_days`) and writes a new note. Each language's edition sizes are in `tools/regions.json` (`languages.<code>.sizes`, MB), made by `site/build_regions.py` from the Kiwix catalog and refreshed weekly by `sizes.yml`, whose commit job only takes whitelisted keys.
- Stand-ins: until kit.json's own Wikipedia is in the kit, the try-it kit adds the best articles' opening paragraphs (top_mini, up to 1 GB) and just the essentials add their text (top_nopic, up to 5 GB) in the same languages (`wikiStandIns`, in `buildPlan` and `estimateBytes`). One that's already small enough comes itself. They go once kit.json's are all in (`dropReplacedWikipedias`, which judges against kit.json's whole list, never the filtered plan, so a plan of just the essentials can't delete a 127 GB Wikipedia), and `dropSamples` keeps a try-it sample while it's still standing in. The builder's Essentials preset shows Wikipedia at `top-text` (`WIKI_PRESET`), the others at `all`, and writes that size, so the kit gets what it shows.

## Setting up

SETUP (`SETUP.command`, `SETUP-Windows.bat`) is a thin script around the kit's own program: it asks the questions and runs `./kit` commands, so a person at a keyboard and an AI agent with options get the same kit.

- Options (`SETUP.command --help`), one for each of the kit builder's settings, which writes them: a preset (`--recommended`, `--essentials`, `--everything`, one at most), `--region`, `--wikipedia`, `--wikipedia-size`, `--no-ai`, `--models`, `--skip`, `--add` (all handed to one `./kit pick`), `--this-computer` or `--drive PATH`, `--share`, `--home-server`, `--no-pause`, `--even-if-tight`, and `--yes` (`-y`), which asks nothing: the first time it needs `--drive` or `--this-computer`, then all of what's picked if it fits with room to spare, else the essentials with a warning, else (or with `--even-if-tight`) it stops and says why. Just the essentials is kit.json's `essentials_only`, so a later run keeps it. An AI agent asks the person the questions, then hands over one command; it never runs the install itself. The answers ride in `KIT_*` env vars across SETUP's restarts (`KIT_YES`, `KIT_PLACE`, `KIT_DRIVE`, `KIT_PRESET`, ...); `KIT_GIVEN` means they were shown once and are reapplied quietly after `./kit update`, then how much fits there (`KIT_ESSENTIALS`), since a preset resets it. A place given that won't do (no drive there, no room) stops it under `--yes` and falls back to asking otherwise.
- Where it goes: "An external drive" or "This computer", with the drives' format and free space (`./kit drives`). The kit moves to `<drive>/TinfoilKit` or `~/TinfoilKit` (`./kit place`; a git checkout stays put, and is copied to another disk). The home folder, not Documents, so iCloud's Desktop and Documents sync never uploads it. On the computer's own disk sync leaves 50 GB free (`keep_free_gb_this_computer`) and keeps `downloads/` out of Time Machine. FAT32 drives, and NTFS on a Mac, are refused up front.
- The first run gets a small kit to try, then the rest when the person is ready: after where and how much, SETUP gets just the try-it kit (`./kit starter on`, about 10 GB for the US Northeast), tests it, says how big the rest is and how long it takes at the measured speed, and offers to open it (under `--yes`: opens it on a Mac, says how on Linux). Running SETUP again on a try-it kit is saying it's ready: it asks the builder's questions (`./kit pick --ask`) unless something already chose (options, or `"picked"`), checks the AI and the room again ("Not now" instead of "Somewhere else"), shows the plan with the time, asks, then `./kit starter off` and syncs. A no puts the try-it kit back (`starter on`). `--no-pause` and `--home-server` go straight on to the rest in the first run.
- Each run after that is `./kit update`, `./kit sync`, `./kit test`, and it says "All set" only when everything finished and passed, lists what didn't otherwise, and handles Ctrl-C.
- A newer download doesn't start over: its SETUP looks for a kit set up before (`./kit kits`: the Mac app's last kit, the home folder, drives with a kit) and runs that kit's SETUP, which updates it; `--this-computer` or `--drive` skips that.
- There's no update schedule: people update whenever they like, and a second SETUP run says it's an update.

## Updating the kit's own code

A drive set up once would otherwise keep its `tools/` and `kit.json` forever, so a source renamed or dropped upstream would fail on every sync until someone edited kit.json by hand. `./kit update` fixes that.

- SETUP runs it first. It installs the newest GitHub release of this repo, then SETUP starts over once on its new copy of itself. Exit codes: 3 installed, 0 nothing to do or the person said no, 1 failed (SETUP carries on with the old code).
- Signed: a release is `tinfoilkit-TAG.tar.gz` plus `tinfoilkit-TAG.tar.gz.sig`, made and signed on the maintainer's computer by `.github/release.sh` (an ssh-keygen `-Y sign` signature, namespace `tinfoilkit-release`). The kit refuses a release unless a key in its own `tools/release-signers` signed it, so a hijacked GitHub account, token or workflow can't push code to drives. GitHub's own source tarball is never used. The kit's program checks the signature itself (Go's Ed25519 and OpenSSH's signature format, since ssh-keygen isn't on every Windows and Linux computer: `verifyRelease`); the tests check a signature ssh-keygen made too. Each release brings the next `tools/release-signers`, so changing keys is a release signed with the old key that lists the new one. A release without a key in that file is refused, since the drive could never update again.
- At a keyboard, it shows what's new and asks before installing. SETUP passes no `--yes`, so people see it there.
- The archive is untrusted: plain files and folders only, all inside its one top folder, under 500 MB. It's unpacked into `data/.kit/update` and checked before anything moves: the needed files exist, its program for this computer runs (`version`), `kit.json` parses, the scripts pass `bash -n` (`checkRelease`). It replaces only `app/`: downloads and the person's data are in other folders. Whatever in `app/` the new release lacks is deleted: `app/` holds only code.
- kit.json merges three ways: the new standard list (`app/kit.json`), the person's (`data/kit.json`), and the standard list they last took in (`data/.kit/kit.base.json`) as the base. The person's changes win and the new version's land everywhere else. An item the release dropped goes, unless its owner changed more than `enabled`. A changed kit.json is rewritten as plain 2-space JSON, the format the website builder makes.
- A copy from GitHub knows its commit: `.gitattributes` sets `export-subst` on `kit/tools/commit`, so `git archive` (releases and Code > Download ZIP) writes the commit into it, and SETUP writes a git checkout's into the app folder it copies to a drive. If GitHub says that commit is newer than the latest release (a ZIP of `main`), the copy stays.
- A git checkout is told to run `git pull` instead.
- The kit's own program (`tools/tinfoilkit-*`) is built from the same commit by CI and again by `release.sh`, which publishes only if the two match. Anyone can rebuild and compare: `build.sh verify [SHA256SUMS]`, or a whole release with `build.sh archive tar tinfoilkit-TAG TAG`. Details in [RELEASING.md](RELEASING.md).

## Downloading

`./kit sync` resolves each item to a version and a list of files with checksums, compares them with `data/.kit/state.json`, then plans, checks free space (`keep_free_gb`), downloads, verifies, installs and prunes.

- **Data stays across versions.** A new version must never download again what's there, and must keep working with older data. Sync adopts a file already in the item's folder by checksum (`matches`), and one in another folder of the same kind (`adopt`: say an item an older version called something else), moving it unless another switched-on item owns that folder. The launcher serves whatever is in `library/` and `models/`, so older editions keep working until a newer one checks out. Only items a try-it sync downloaded are marked `"sample": true` in state.json; the next full sync removes those kit.json doesn't switch on and clears the mark from the rest, so a book switched off long ago stays.
- **Several connections.** A file of 32 MB or more comes over 8 connections at once, each a curl with its own byte range (`downloadParts`). curl's `-C <start>` beside the `Range` header makes it fail (exit 33) unless the server sends the file from that byte, so nothing lands in the wrong place. Parts go out in order, so the file grows from its start: exFAT and NTFS write zeros into a gap before writing past it. Near the end, an idle connection takes the second half of the part with the most left. Which parts have arrived is in `<file>.parts` (`{"size": N, "done": [[start, end], ...]}`, end exclusive), written after an fsync so it never claims too much, until the file is whole: a full-length file with a `.parts` record (or aria2c's `.aria2`) isn't whole. A download one connection began carries on in parts from its end. A server that won't send parts gets one connection (`curl -C -`), keeping what arrived from the start. `"downloader": "curl"` in kit.json means one connection, `"aria2c"` uses aria2c, and auto uses aria2c only to finish a download it began. Against a server that caps each connection at 5 MB/s, 0.1 s away, 200 MB took 40 s over one connection and 5.8 s over eight. The tests make files of 32 KB or more come in parts (`KIT_PART_MIN=16384`); the mock serves `NO_PARTS`, `SLOW` and `FLAKY` and logs what it sent to `served.log`.
- **Programs are pinned.** `tools/pins.json` names each program's build and its SHA-256, and every release carries it, signed with the rest. Sync fetches that build (GitHub by its tag, since llama.cpp's builds are soon off the first page; Kiwix by the file name the pin gives, without reading the folder's listing, which Kiwix limits) and refuses a file whose publisher's checksum differs from the pin. A pinned build its publisher took down says so. Books, models and map data aren't pinned: they change upstream on their own schedule and the kit wants the newest. Photon is the one exception to a pin: when no address database is published for the pinned version any more, it takes the release that opens the newest one, since a pinned Photon that can't open its data is no use. `"pin_programs": false` in kit.json takes the newest builds instead; the test kits (`drive_kit*.json`) set it because the mock internet serves its builds under test versions.
- `./kit pins` (weekly in `pins.yml`: a read-only build job plus a commit job, like `sizes.yml`) resolves exactly as the plan does, so Photon matches the newest database. A program it can't look up keeps its old pin. A file that changed under the same version keeps its old pin and fails the run, so nothing is committed until someone finds out why. A commit a workflow pushes starts no checks, so `check.yml` can be run by hand, and `release.sh` says so when the newest commit has none; it also refuses to release with no pins.
- **A busy server gets the wait it asks for.** A publisher that answers 429 (too many requests) or 503 is asked again after its `Retry-After` (5 minutes at most), or after 15 s, 30 s, 1 and 2 minutes, saying so as it waits (`httpGet`); one still busy after that is asked once a time, without waiting, for 10 minutes. curl's `--retry` asks again within seconds, waits out a `Retry-After` silently, and skips a 429 that a Mac's curl reports as exit 56. Other hiccups (a timeout, a failed lookup, a 5xx, a dropped connection) get three more tries 2 s apart. Without a pin, a Kiwix folder's listing is read once a run, even when that fails. The kit's own servers answer 503 while they start, so `./kit test` gets curl's quick tries (`localGet`).
- Only llama.cpp follows `llama_cpp_channel` (its builds are nightly prereleases). Every other GitHub program takes a full release while it has one, and a prerelease only when there's nothing else.
- **Half-finished downloads** are `<file>.partial` next to their destination (archives and the Photon dump: `downloads/.partial/`). `state.json` records each one's version under `partials`:
  - a partial of a different version under the same file name (models often keep their names) is discarded, not resumed into a corrupt file;
  - at the start of a sync, partials that a newer version made useless are deleted (they can be 100 GB); those of switched-off items are kept;
  - free-space checks count what a partial already has.
- **Exit codes:** `sync` exits 1 if any item failed or couldn't be looked up, and 130 on Ctrl-C (everything finished is saved). `last_sync` is set only after a fully clean run; the page shows it as "Refreshed (date)" in its header. `plan` and `sync` exit 1 straight away when nothing could be looked up (offline, or a Wi-Fi sign-in page answering instead).
- `refresh_days` on a library entry (Wikipedia: 365) keeps the installed edition until it's that many days old, as long as its files are all there; the plan marks it `later`. Naming it in `--only` gets the new edition now. Library only: a map or model whose source changes (a new region) must never wait.
- The Kiwix catalog is cached only after it parses, so a sign-in page can't poison the cache.
- Each download is verified against what its source publishes: Kiwix's `.sha256` file, Hugging Face's LFS sha256, GitHub's release asset digest, Maven's `.sha1`, npm's sha512 integrity hash, Geofabrik's and Photon's `.md5`.
- **Drives are exFAT, which has no symlinks.** Runtime versions are tracked with `CURRENT` pointer files instead, and archives are extracted on the internal disk, then copied over with symlinks resolved.
- An old version is deleted only after the new one verifies. The previous runtime version is kept, and the launcher falls back to it if the current binary won't run.
- Items install in priority order. Runtimes (priority 0) go first because the map steps need Java and pmtiles.
- Every remote endpoint can be overridden with an environment variable, which is how the tests point the kit at mocks: `KIT_KIWIX_CATALOG`, `KIT_KIWIX_RELEASES`, `KIT_GITHUB_API`, `KIT_HF`, `KIT_ADOPTIUM_API`, `KIT_MAVEN`, `KIT_NPM`, `KIT_GITHUB_WEB`, `KIT_PROTOMAPS_BUILDS`, `KIT_PROTOMAPS_BUILD_BASE`, `KIT_PHOTON_DUMPS`, `KIT_GEOFABRIK` (`tests/env.sh`).
- At the end of every sync, `data/.kit/portal.html` is rebuilt from the template with the map assets embedded.
- `plan` shows `~` before a size it estimates (map tiles) and `?` when the size is unknown.
- While a big file downloads, sync shows what has arrived, the speed and the time left, for the file and for everything after it in this sync (`progressLine`). On a terminal that line is written over every second, so the part for everything is left out when it wouldn't fit on one line.

## Starting the kit

Both launchers run `./kit open`, which starts the servers, prints what it's doing (the Mac app reads those lines), and runs the sharing gate and the notes server itself. It needs nothing installed: no Python, and no curl to check its servers (stock Ubuntu and Debian have none). When a program on the drive won't run (say, a library Linux lacks), it prints the reason.

- **Library:** kiwix-serve on port 8888, serving the library plus the kit page as `--customIndex`. It serves the page `./kit sync` built (`data/.kit/portal.html`, with the map inside) whenever it exists, and the bare template otherwise.
- **AI:** llama-server on port 8080 in router mode, with `--models-max 1` and `data/.kit/presets.ini` (`aiServer`), which names each model folder's weights and vision projector, with `load-on-startup` for the default model. Not `--models-dir`: scanning a folder, llama-server also takes an `mtp-`, `dspark-` or `dflash-` file beside the weights as a speculative decoding draft, and Gemma 4's draft with its projector aborts it as the model loads ([llama.cpp#30698](https://github.com/ggml-org/llama.cpp/issues/30698)). The paths start at the kit folder, where llama-server runs, because the file can't hold a `#` or `;` and a drive's name might. `./kit test` starts it the same way, with a list of its own (`presets-test.ini`). `tools/ai-chat.json` gives its chat page the kit's safety rules.
- **CORS:** the AI, map tiles and address search allow exactly one origin, the page at `http://127.0.0.1:<library port>`, so other web pages open on the computer can't read their answers (llama-server echoes `--cors-origins` back verbatim, so it must be one). That's also why the page redirects `localhost` to `127.0.0.1`. Sharing doesn't change it: other devices reach every server through the gate, on the page's own address. GraphHopper (directions) always allows every origin and has no setting for it.
- **Maps:** `pmtiles serve` on 8090, Photon on 2322 and GraphHopper on 8989, the last two run by the kit's Java. Their memory comes from `kit.json` (`geocoder_heap` 3g, `routing_heap` 2g). `--no-maps` skips them and saves about 5 GB.
- **Notes and pins:** the program's own server on 8095 (`data_port`); when it doesn't answer, the page keeps them in the browser and says so. The page's address carries the port (`&data=`). See [The kit page](#the-kit-page).
- **Sharing:** every server listens on 127.0.0.1. With sharing on (Share with family on the kit page, `./kit share on`, or `--share` for one run) the launcher also starts the gate on port 8000 for the home network, behind the access code, and prints the address, the code and a QR code. It starts and stops the gate as it runs, when the page or `./kit share` asks (`sharer` in `gate.go`).
- **Staying awake:** `caffeinate` on a Mac, `systemd-inhibit` on Linux, `SetThreadExecutionState` on Windows (while sharing).
- **First model:** the default, unless its files take more than 60% of memory; then the biggest model that fits, else the smallest. `--model=NAME` overrides. `KIT_MEMORY_MB` fakes the memory size for tests.
- **Ports:** a server already on a port counts as the kit's only if it answers like one (the page's title, or `/v1/models` JSON). Otherwise the library or AI starts on the next free port, and the page's address carries it. Map ports are baked into the page at sync time, so they don't move.
- **Library on ::1:** kiwix-serve 3.8 refuses 127.0.0.1 when the loopback has a second IPv4 address (libkiwix keeps only the last one of each interface). The launcher then starts it on ::1 and forwards 127.0.0.1 to it.

## Sharing and home servers

kiwix-serve, pmtiles, Photon and GraphHopper have no passwords, so they stay on 127.0.0.1 and one small server in the kit's program (`gate.go`) sits in front of them for the home network.

- **Routes:** `/ai/` goes to llama-server, `/tiles/`, `/geocoder/` and `/routing/` to the map servers, `/data/` to the notes and pins, everything else to kiwix-serve. llama-server's own chat page asks for its API at the root (`/v1/`, `/props`, `/models`, `/slots` and the rest in `aiPaths`), so those go to the AI too; the library has nothing there. The kit page gets `window.KIT_GATE` (the address and code) injected after `<head>`, and then asks the gate for the AI and the map instead of their ports. On the computer itself the page comes straight from kiwix-serve, so it asks the notes server's `/share`, which answers while the gate does (`gatePort`): the address, the code and the QR code. Answers stream through as they're written. The servers' `Access-Control-*` headers are dropped. llama-server's `/tools` and `/cors-proxy` (tools that run things, a web proxy) get llama-server's own "feature disabled" 403 from the gate however they're spelled, so they stay off for the network even if someone turns them on locally; its chat page asks for `/tools` on load and copes with the 403. An answer the gate gives without reading the request's body (that 403, a 401) closes the connection, or the body would be read as the next request.
- **Access code:** 8 random digits in `data/.kit/share.json` (never kit.json, which people share) with a random key. A device types it once (or opens the link the QR code and Share carry, `/?code=`) and gets a cookie: an HMAC of the code, `HttpOnly`, `SameSite=Lax`, a year. Programs send it as `Authorization: Bearer`. A new code (`./kit share new-code`) signs everyone out; the gate rereads the file when it changes. 10 wrong codes per 10 minutes per address, then 429.
- **Who it answers:** only private source addresses (10/8, 172.16/12, 192.168/16, loopback, link-local, 100.64/10 for CGNAT and Tailscale), and only when the Host is an address, a bare name or a home network name (`.local`, `.lan`, `.home`, `.internal`, `.home.arpa` and a few more): a website can't point a name of its own at the kit (DNS rebinding). Plain HTTP, so it's for your own network, not a café's. IPv4 only.
- **Share with family** (`#share`, under More): Turn on sharing, New code and Turn off sharing, then the message to text: what the kit is, and the link with the code. Only the computer the kit runs on changes sharing: the page asks the notes server (`PUT /share`), which starts or stops the gate in the same program and saves `share_on_network`, so the next start shares too. The gate marks what it passes on (`Tinfoilkit-Gate: 1`) and lets only GET through to `/data/share`, and the notes server offers the buttons (`canChange`) and takes a change only without that mark: a phone with the code can't turn sharing off or change the code for everyone. `./kit share on|off` asks the running kit the same way. Another window of the kit that runs the gate keeps it, and the page says so. The gate swaps a link's code for the cookie and answers 303 to the same address without it, before any page loads: the code isn't left in the address bar or a bookmark, and no page that had it can pass it on as a Referer. The link works only from a home network address, a stale one counts toward the 10 tries, and anyone with the message gets in from the home network until `./kit share new-code`, as the page says. The address it carries is the one the device used when that's an IP address, else `lanIPs()[0]` (for this computer, or a name: not every phone can look up `homeserver.local`). Copying uses the clipboard API on 127.0.0.1 and a selected hidden textarea over the home network's plain HTTP, where browsers turn that API off.
- **QR code:** its own encoder (`qr.go`: byte mode, level M), checked bit for bit against Nayuki's qrcodegen and decoded with jsQR when written; `tests/share_test.py` pins three codes. In the terminal it's drawn with half blocks, in the page as SVG.
- **Port:** `share_port`, 8000. If another program has it, the launcher takes the next free one for that run and says how to pin one; `./kit share` finds where the gate really is (`gatePort`, by its `Server: TinfoilKit` header).
- **Starting with the computer:** on Linux, a systemd user service (`Restart=always`) and `loginctl enable-linger` (tried without sudo, then with `sudo -n`) so it starts at boot; no root service, so it runs as the person. On a Mac, a LaunchAgent (`KeepAlive`), which starts at login, so a Mac server needs automatic login; macOS may refuse it for a kit on an external drive. `./kit share on|off` tells the running kit, or restarts the kit the computer started if it doesn't answer. UNINSTALL runs `./kit autostart off` first.
- **Windows:** autostart is `Tinfoil Kit.cmd` in the Startup folder (`%APPDATA%\...\Startup`): UTF-8 with `chcp 65001` for any folder name, `%` doubled, starting Open Tinfoil Kit for Windows minimized with `--no-browser` if the kit is still there, at sign-in. A Windows server stays signed in (locked is fine). `autostart on` also starts it now; `off` deletes the entry but can't tell which window it started, and `share on|off` can't restart the kit there, only tell it. The gate turns on the console's colors for the QR code, and doesn't set `SO_REUSEADDR` (on Windows it would share a port another program holds). Windows Firewall asks once whether tinfoilkit-windows-x64.exe may listen; Open Tinfoil Kit and `autostart on` say to allow it, and the GUIDE covers a refused prompt and Public networks. SETUP's `stop_kit` and UNINSTALL stop the kit's window, and UNINSTALL deletes the Startup entry if it's this kit's.
- **SETUP --home-server** carries the flag in `KIT_HOME_SERVER`, since SETUP starts itself again after moving and updating the kit. At the end it runs `./kit share on`, `./kit autostart on` and `./kit share`, instead of asking to open the kit.

## Copies

`./kit copy` (`copy.go`) puts a kit of its own on another drive: for family and friends, or a spare. It copies, never downloads, so it works in an outage.

- **Parts** (`copyParts`): the programs (the app folder as a release has it, and every computer's llama.cpp and kiwix-tools: they always go, as `./kit test` wants the AI server even with no model), the map (tiles, viewer, roads and every computer's Java, pmtiles, GraphHopper and Photon), its address search (the database), then each AI model, book and extra with its title and group from the builder's list. A program takes only its CURRENT version. An item with anything missing on the drive isn't offered.
- **Sizes:** a file takes whole 128 KB clusters on exFAT. A drive keeps 1 GB and 1% free; erased, it loses 300 MB more to its partitions.
- **Presets** are wish lists, most important first, and `copyFill` takes each that still fits: Essentials is the programs and the essential books (priority 1, `"essential": true`, or Wikipedia's best articles); Essentials plus maps adds the map, then address search; Everything that fits adds the map, the other books by priority, address search after the priority-2 books, then extras. The AI goes right after the programs only when asked (the smallest model). With a drive, `--json` says what that copy would be and what it does to the drive, without copying.
- **Erasing** (`copyChoose`): only when it must. A drive that isn't exFAT (`copyFormatProblem`: FAT can't hold big files, APFS and HFS+ are Mac-only, and Macs can't save to NTFS) or too full for what goes on it is erased; a kit on it is replaced instead, keeping what's the same and its notes. Either needs the drive's name, typed or as `--erase NAME`. A TinfoilKit folder with anything but a kit in it is never replaced (`alone`), only erased with the drive. On a Mac, `diskutil eraseDisk ExFAT NAME GPT` erases the disk the volume is on, past an APFS container to its physical store (`macDiskIn`), and only if no other volume is mounted from it and it's neither the startup disk, the kit's own, nor an internal one. Windows and Linux need an administrator to format a drive, so the kit says how instead.
- **Copying:** into `TinfoilKit.partial` on the drive, renamed to TinfoilKit once it checks out. A kit being replaced is renamed to that first, and what the copy won't have is deleted from its app and downloads (`pruneCopy`). A file already there at the right size is kept (a copy that stopped carries on, a replaced kit keeps its books), since reading back checks it. A file whose SHA-256 isn't what state.json says stops the copy: this kit's own copy is damaged.
- **The copy's data:** kit.json is this kit's with only what the copy has switched on (address search off by `geocoder_country: ""` when it stays behind), `picked`, sharing off, a default model it has, and no `essentials_only` or `starter_only` to narrow it; state.json lists only what it has, a program's other versions dropped; the notes and pins only with `--notes`, never over a kit's own; the built page, INVENTORY.md, the launchers and `card.html`.
- **Reading back:** every file, once all are written, so a failing drive or one that's smaller than it says shows up: a fake drive overwrites its first files once it's full. What's read must come from the drive, not the computer's memory: on a Mac, writes and reads use `F_NOCACHE`, and `Sync` is `F_FULLFSYNC`; on Linux, each file is synced and dropped from memory (`posix_fadvise(DONTNEED)`) before it's read; on Windows the reads use `FILE_FLAG_NO_BUFFERING`, in whole sectors from a buffer aligned to 4 KB, falling back to a plain read if the drive refuses. A file that reads back wrong is copied again and read once more; still wrong, the copy stops.
- **Then** it runs the copy's own program for this computer from the drive, `test`, on ports of its own. The card (`copyCard`: how to start it on each computer, what's on it) is in the copy's `data/.kit` and this kit's, for the page to print. `data/.kit/copy.json` has the step, bytes done, speed and time left; one copy at a time, and none while a sync runs (the kit's lock).
- Tests: `KIT_DRIVES` is a folder of drives, `KIT_DRIVE_BYTES` their size, `KIT_DRIVE_FORMAT` their format, and erasing one empties its folder.
- **On the kit page,** More > Make a copy opens `/copy` on the notes server's own address, in a tab of its own: the kit page's file, which sees where it is and shows only Make a copy. The kit page's address also serves the books, whose pages can run scripts, and none of them may start a copy, let alone erase a drive. So `/copy` and what it asks (`GET /copy/info`, `GET /copy/plan`, `PUT` and `DELETE /copy/job`) answer only their own address: an Origin must be it, and Sec-Fetch-Site same-origin, except for following the link that opens the page. Never in a frame (`frame-ancestors 'none'`, `X-Frame-Options`) and never through the gate (`copyHereOnly`); the page's CSP lets it load nothing and reach only this server. It runs `./kit copy --json` for what it shows, then `./kit copy --yes` with the drive's name as `--erase` once it's typed, and follows `copy.json`, whether it or a terminal started the copy (`pid`). Stop writes `copy.stop`, which the copy takes as Ctrl-C. The card prints from `/copy/card`.

## The kit page

`tools/portal.html` is plain HTML and JavaScript with no build step. The core logic is a `Kit` object, exported with `module.exports` so node tests can run it; browser-only code is in a separate function.

- **Ask:** two buttons, so it's plain which one wakes the AI.
  1. **Ask the AI:** the AI writes search queries (fallback: keyword extraction, `fallbackQueries`).
  2. kiwix full-text search runs across every book. Queries stay short because Xapian ANDs every word.
  3. The top articles are read and an answer streams back with `[n]` citations. "Done in" counts from the click, search included, so it compares with Search's.
  4. **Search** (and Ask the AI with the AI off) runs steps 2 and 3 on the question's own words and shows the passages in full, with no request to the AI: seconds, on little power. **Have the AI answer from these** hands those passages to step 3, with no second search.
- **Map questions:**
  - `Kit.isMapQuestion` uses a deliberately strict regex. "How far should I stay from a downed power line" still goes to the library.
  - Map questions go to an AI tool-calling loop with the tools `search_places`, `find_nearby` and `get_directions`, and the results are drawn on the Map tab.
  - It falls back to the library when the AI calls no tool, or when the AI is off and search finds nothing.
  - With the AI off, `guessMapIntent` parses simple questions on its own.
- **Map tab:**
  - MapLibre GL 5.x as a UMD build (6.x ships ESM only) with the @protomaps/basemaps 5.x "light" style.
  - Fonts (Noto Sans Regular, Medium and Italic, ranges 0-255, 256-511 and 8192-8447) and the "light" icon sprites are embedded as base64 and served through `maplibregl.addProtocol` (`kitglyph://`, `kitsprite://sprites/light`), because kiwix-serve can serve only one custom page.
  - A search box with suggestions; Drive/Walk directions with clickable steps; "nearest" buttons by category; and "Set home", kept in the kit. A laptop has no GPS, so home is where searches start.
  - The search box takes coordinates as GPS units and paper maps write them (decimal, degrees-minutes-seconds, N/S/E/W before or after; `parseLatLon`, which turns down "45 N 100 W" since grid cities have addresses like that). Clicking the map shows that spot's coordinates, decimal and DMS, with Copy, Pin this place, Directions here and Set as home; every place popup shows coordinates. Pins (name, note, coordinates) are kept in the kit like home; search lists them first, and directions, the map tools and the AI's system prompt know them by name (`findPin`: "our meeting place" finds "Meeting place").
- **Notes** (`#notes`, under More): what the household needs the AI to know (allergies, medicines, where to meet). Ask's system prompt carries them (`Kit.withNotes`, the first 4,000 characters), and so does the map AI's. They, home and pins live in `data/` so they move with the drive, survive a new version and reach phones through the gate:
  - The kit's program (`data.go`, also `tinfoilkit data` on its own) serves `GET/PUT /notes` (`data/notes.txt`, plain UTF-8, so a text editor works too; a Notepad BOM is dropped) and `GET /places`, `PUT /places/home`, `PUT/DELETE /places/pins/ID` (`data/places.json`, other keys in it kept). It listens on 127.0.0.1 and answers only the kit page: the Host must be 127.0.0.1 or localhost (DNS rebinding), and an Origin, when there is one, must be the page's (`--library` port). Saves are JSON only (`PUT`, so a preflight), up to 1 MB, 100,000 characters of notes, 1,000 pins. Each save writes a `.new` file, fsyncs it and renames it over the old one. It never creates the data folder: with it gone (the drive unplugged), saves fail instead of starting a new kit.
  - Two devices: notes carry a version (the first 16 hex of their SHA-256), and a save from an older version gets 409 with the current notes; the page offers Keep mine or Use theirs. Places answer each change with the whole list, so another device's pins show up.
  - The page saves notes 0.8 s after typing stops, on leaving the box and on leaving the page. When the server can't be reached (the kit stopped) it keeps them in `localStorage` (`kit.notes` with the version they began from, `kit.pins`, `kit.home`) and says so, then moves them into the kit the next time it answers: browser pins by id, a browser home only if the kit has none, notes only if the kit's haven't changed since (`Kit.notesMerge`), else the conflict card.
  - A launcher finds a notes server already running by its `/` answer (`"notes": "/notes"`). `./kit test` starts it and reads both files.
- **Print the essentials** (`#print`, under More):
  - `Kit.PRINT` lists the few pages worth having on paper, most important first, each a page range of a PDF in one or more books, best first: the try-it kit's medicine, water, post-disaster and military medicine books, and Ready.gov's power outage sheet where a kit has Ready.gov. `Kit.printList` keeps those the catalog has and links each at `#page=` its first page; the page shows the first link that answers a one-byte range request, and leaves out a document no book has.
  - The page numbers are the PDF's own, as a print dialog takes them, checked in the editions the comment above `PRINT` names. A new edition of one of those books needs them checked again: read the PDFs' text (libzim and `pdftotext`) in a workflow run on a branch, since a cloud session can't reach download.kiwix.org.
  - Under the list, the household's own page: home and pins with their coordinates, the notes (or lines to write on), and the nearest hospitals, clinics, pharmacies, fire stations and police from Photon, as the crow flies, with fewer lines to write on when those take the room, so it stays one sheet. The print CSS makes the page white in either theme and, from this tab, prints that page alone.
- **Header:** the name, a status button and three tabs, so a phone's header stays two rows. The status button says how the kit is in a word (Ready, Starting, AI off, Library error, and Shared) and opens the pills it stands for: the library, the AI, sharing and when SETUP last refreshed the kit. The tabs are Ask, Map and Library; More opens the pages used now and then: Notes, Share with family, Print the essentials, Make a copy ("Copies" above) and AI chat (llama-server's own chat page), those two in a tab of their own, and Help. A click elsewhere or Escape closes either. Pages are links (`#ask`, `#map`, `#library`, `#notes`, `#share`, `#print`, `#help`), so the keyboard reaches them and the address remembers the page. The status line is `role="status"`; map results, nearest places and route steps are buttons.
- **Template tags:** kiwix-serve renders `--customIndex` as a Mustache template. The template contains exactly one tag, `{{root}}`. The built page starts with a set-delimiter tag (`{{=<% %>=}}`) so the embedded code survives rendering.
- The website's Try it demo (`site/components/demo.jsx`) is a copy of the page, with answers written ahead of time and sharing faked, so a change to the page changes the demo too. `tests/site_test.py` compares their tabs, More menu and the words on Ask, Notes, Share with family, Help and Print the essentials.

## Maps

- **Tiles:** Protomaps' daily planet build (list at `build-metadata.protomaps.dev/builds.json`, files at `build.protomaps.com`). `pmtiles extract` cuts the world at zoom 0–7 and the region's box at zoom 8–15; `pmtiles merge` combines them (inputs must be clustered and must not overlap); `pmtiles verify` checks the result. Served as `/basemap/{z}/{x}/{y}.mvt` and `/basemap.json`.
- **Address search (Photon 1.x):** a prebuilt database from `download1.graphhopper.com/public/`, found by reading its region table: region, then continent or country folder, then `photon-db-<slug>-<major.minor>-latest.tar.bz2` with an `.md5`. Photon refuses databases built for another version, so the kit picks the Photon release that matches the newest available database. Where nobody publishes one for the country alone, the continent's is used. "Nearest" calls `/reverse?radius=40&include=osm.amenity.hospital,...` and falls back to `osm_tag=` filters for older databases.
- **Directions (GraphHopper 11.x, pinned):** the kit writes the config: profiles `car` (with CH speed-up) and `foot`, encoded values matching the built-in `car.json` and `foot.json` at tag 11.1, and `graph.locktype: simple`, because exFAT can't do native file locks. The import uses `RAM_STORE` with `routing_import_heap` (auto: 12g, or 60% of the computer's memory if that's less); if Java runs out of memory (`-XX:+ExitOnOutOfMemoryError` exits 3), it builds again with `MMAP`, which needs far less. Serving uses `MMAP`. Road data is Geofabrik's extract for the region (for places nearby, merged into one file). The network is rebuilt whenever the road data or the GraphHopper version changes, which takes 10–40 minutes.
- **Java:** Adoptium Temurin 21 JRE, from `api.adoptium.net`.
- **Regions:** `tools/regions.json` lists the places "Where do you live?" offers, each with its map box, road data, address search, home, units and languages. The default is the US Northeast: street detail and directions for New England, New York, New Jersey and Pennsylvania, address search for the whole US, home in New York, and a low-detail world map, about 20–30 GB.

## What kit.json holds

- **Models:** `Inkling-2-Mini` (the default), `Qwen3.8-27B`, `Gemma-4-26B-A4B`, `Gemma-4-12B` (for 16 to 24 GB of memory) and `Gemma-4-E4B` (small and fast). llama.cpp's nightly builds are used (`llama_cpp_channel`), since its stable releases lag behind new models. Gemma 4's repos also have MTP drafts (`mtp-*.gguf`), which the kit doesn't download or load (see AI above); a kit that has them from before deletes them at its next full sync, as it does any file kit.json stops listing (`dropUnlisted`).
- **Library:** about 40 ZIM files, by priority: medical (WikiMed, MedlinePlus, CDC Travelers' Health, military medicine, LibreTexts medicine), preparedness (Ready.gov, Urban Prepper, Learning Self-Reliance, post-disaster, water treatment, food, knots), repair (iFixit, CD3WD, US Army publications, Stack Exchange sites), and reference (Wikipedia with images, about 127 GB in English, or a smaller size; Wiktionary, Wikibooks, Wikivoyage, Wikiversity, LibreTexts). Off by default: Survivor Library, Khan Academy, all of Project Gutenberg.
- **Extras:** Ollama's installer (off by default).
- **First sync:** from about 20 GB (just the essentials) to about 900 GB (everything); 200–300 GB for the recommended kit, depending on the AI models the computer runs and the map (`./kit estimate`). The weekly `refresh builder sizes` workflow lists any source that stops resolving.

## The Mac app

On macOS 15 and later a downloaded script (`SETUP.command`) opens only through System Settings > Privacy & Security > Open Anyway, which people miss. A notarized app gets macOS's ordinary "downloaded from the Internet" question instead.

Releases leave the app out until the maintainer's Mac can sign and notarize it ([RELEASING.md](RELEASING.md#signing-the-mac-app-once)), and the website offers no download until then. Setup is the command an AI hands over: it downloads `TinfoilKit.tar.gz` (or the Windows zip) with curl, which doesn't mark files as downloaded from the internet, so neither macOS nor Windows stops SETUP.

- **What it is:** `Tinfoil Kit.app`, the website's Mac download once it's signed (`TinfoilKit-Mac.zip`). A small Cocoa app in one file (`mac/TinfoilKit.m`, no Xcode project) plus `mac/app.sh` for its file work, around a copy of the kit in `Contents/Resources/kit`. Nothing from other publishers inside.
- **First open:** from Downloads (App Translocation) it offers to move itself to Applications. Then "Set up Tinfoil Kit" copies its kit to `~/Library/Application Support/TinfoilKit/Setup/TinfoilKit/app`, lifts the quarantine mark, opens that copy's SETUP.command in Terminal and quits. SETUP's first question moves the kit to the drive or `~/TinfoilKit`, as from a ZIP. When the app is in Applications, SETUP says to open it in an outage, and "Open the kit now?" opens it.
- **After that:** it finds the kit (the one it opened last, `~/TinfoilKit`, `/Volumes/*/TinfoilKit`; it asks which if there are several) and runs the kit's own `app/Open Tinfoil Kit.command`, with its output in a window: Open in Browser, Update… (SETUP in Terminal), Remove… (UNINSTALL in Terminal). Closing the window or quitting stops the kit. A kit with no books yet gets "Finish setting up". If the drive it opened last isn't plugged in, it names the drive. SETUP writes `last-kit` too, so that works before the app has opened a kit.
- **Why Terminal still:** SETUP asks questions and runs for hours, and it's the same script on every computer. The app is a door to it, not a second installer. The kit inside is only for the first setup; SETUP and `./kit update` keep the kit current after that.
- **Building and signing:** `mac/build.sh KIT OUT [VERSION]` compiles it (arm64, macOS 12 or later), writes Info.plist and signs it: with `KIT_MAC_SIGN` (a Developer ID Application certificate) under the hardened runtime with a secure timestamp, otherwise ad hoc. With `KIT_MAC_NOTARY` too (a notarytool keychain profile) it sends it to Apple, waits, staples the ticket so it opens offline, and checks it with `spctl`. Only on the maintainer's Mac, from `.github/release.sh`: workflows get no secrets, and the Developer ID key stays on that Mac like the release key.
- **Tests:** `tests/mac_test.py` (quick gate) covers app.sh: finding kits, setup, update, remove, remembering, moving, and the icon. The drive test builds the app on the Mac runner (ad hoc), puts it in `~/Applications`, opens the drive's kit with it, checks the page, quits it and checks the servers stopped, then with the drive unplugged sets up the home-server kit from the app's own copy. `KIT_APP_ANSWERS` presses its buttons (numbered from 1) and logs each question; `KIT_APP_OPEN`, `KIT_VOLUMES` and `KIT_APPLICATIONS` stand in for Terminal, `/Volumes` and `/Applications`. Notarizing can only be tried on the maintainer's Mac: `.github/release.sh mac`.
- **Icon:** `mac/AppIcon.icns`, the mark on a paper rounded square, made by `site/build_images.py`.

## Gotchas

- Kiwix's `_ftindex:no` tag shows up even on books that do have a search index, so the kit searches every book.
- kiwix-serve requests a favicon, so the page sets `<link rel="icon" href="data:,">`.
- macOS bash 3.2: no `set -u` with empty arrays, and no `mapfile`.
- `pmtiles` has no `--version` flag. Use `pmtiles version`.
- MapLibre rewrites `kitsprite://light` to `kitsprite://light/.json`, so the sprite URL needs a path: `kitsprite://sprites/light`.
- A CSS `display:flex` overrides the `hidden` attribute, so the page has a global `[hidden]{display:none !important}`.
- An archive item without a `binary` is judged installed by its files (`evaluate`), or it would download again on every sync.
- go-pmtiles names its Mac assets `go-pmtiles-<version>_Darwin_arm64.zip`; they are signed.
- Map data uses its Last-Modified date (YYYY-MM-DD) as its version.
- Downloaded files are untrusted. Inspect them as text; never run downloaded code to see what it does.
- On exFAT, macOS keeps Finder metadata in `._name` files beside the real ones (opening a book from Finder is enough). A glob for `*.zim` matches them in most languages; bash's `*` doesn't. The launcher and `./kit test` delete them from `library/` and `models/`.
- Windows won't move the folder of a program that's running, and a lock file opened to append can't be locked there.
- Fedora 45 moved to OpenSSL 4, while llama.cpp's Linux build needs OpenSSL 3, so the AI needs `openssl3-libs` there (the GUIDE says so).

## Tests

Everything runs against mocks of every download source and map server, so no test downloads the real thing. AGENTS.md says which to run when.

- **Quick gate (`tests/check.sh`, every push):** formatting and lint for every language, parse checks, kit.json validity, `site/sources.json` freshness, the Windows scripts' line endings and labels, the workflows' rules (`actions_test.py`), the contribution gate (`pr_gate_test.js`), the Go checks, and that what agents read names only real commands (`skills_test.py`). Then:
